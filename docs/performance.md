# PostgreSQL 并发与性能验证

本页对应 [Doggy_final.md](../Doggy_final.md) §17.2 的本地软件验证。性能结果必须连同数据量、并发、进程数、测试时长和机器环境一起阅读；一次本机运行不代表生产容量、月度可用性或真实项圈链路已验收。

本页保留首次性能阶段的原始负载、结果与当时测试统计；后续运营阶段未重跑该基准。设备凭证阶段因涉及遥测热路径已再次执行，当前结果与 Worker 满批等待调整见 [协作流程](process.md)。

## 验证目标与口径

| 项目 | 项目文档目标 | 统计口径 |
| --- | --- | --- |
| 普通读取 API | P95 < 500ms | 真实 HTTP 请求完成并读取响应的耗时；排除建库、预置数据和启动阶段，记录实际接口及并发 |
| 已接收遥测处理 | P95 < 10s | `device_events.processed_at - received_at`，包括排队；另列 Worker 开始处理前的等待 |
| 规则满足后告警持久化 | P95 < 30s | 使用满足围栏确认规则的事件 `processed_at - received_at`；告警包含在该事件的投影事务内，统计的是应用层投影完成代理 |
| 数据正确性 | 重复不产生重复业务结果、旧数据不覆盖新状态 | 并发幂等、重复/乱序、独立 Worker 协作、最新位置和通知关系另作断言，不能只看请求成功数 |

现场越界到推送服务接受的 60 秒目标、手机送达、真实设备采样/网络、月度 99.5% 可用性不在本地压测的证明范围内。offline 的通知仍是 `simulated`，不当作手机收到提醒。

`processed_at` 在事务提交前写入，因此投影完成指标不直接测量 WAL 持久化或 COMMIT 确认；相关告警与通知的存在、最终状态由后续已提交查询核验。`safety_events.occurred_at` 是设备业务时间，不能替代服务端持久化时间。

## 运行与隔离

性能运行使用 PostgreSQL/PostGIS、合成账号/宠物/位置和 offline 模式，创建独立随机数据库。配置 URL 用于连接维护服务器；压测数据不得写入现有 `doogy`、恢复副本或 SQLite 文件。

运行前启动本项目数据库，并保留现有环境文件：

```powershell
npm.cmd run postgres:up
npm.cmd run postgres:perf
```

`postgres:perf` 自动构建，加载 `.env.postgres`；`TEST_DATABASE_URL` 优先于 `DATABASE_URL`。维护账号需要创建/删除本次测试数据库和安装 PostGIS 的权限。默认报告写到 `data/performance/postgres-时间戳.json`，报告不包含账号/设备令牌、精确坐标或业务数据库连接 URL。

一键入口为 `start.bat .env.postgres perf`，先同步依赖和编译。API 与 Worker 的正常运行入口、备份恢复入口继续保留。SQLite 离线运行仍使用 `start.bat`，不依赖 PostgreSQL 性能工具。

```powershell
# 小数据烟测，验证工具链；不作为容量结论。
npm.cmd run postgres:perf -- --quick
./start.bat .env.postgres perf --quick

# 指定一个尚不存在的报告文件，不覆盖旧结果。
npm.cmd run postgres:perf -- --report ./data/performance/my-run.json
```

报告包含 `checks`、`passed`、`cleanup` 和自有进程停止结果；正确性、阈值或清理检查失败时返回非零退出码。工具创建名称为 `doogy_perf_随机UUID` 的库，只清理本次创建的库及子进程。测试临时 API 使用随机端口，不占用用户的正常 API 端口。

避免同时运行另一套性能测试、全量测试或耗资源任务；机器上其他项目、Docker 资源限制、缓存和系统调度都会影响结果。复验要保留报告中的环境和工作负载参数。

## 固定工作负载

| 阶段 | 默认 `trial` | `--quick` |
| --- | --- | --- |
| 合成对象 | 20 个家庭、20 只宠物、20 台设备、20 个圆形围栏 | 4 套对象 |
| 历史数据 | 20,000 个位置和关联已处理事件，每宠物 1,000 点 | 120 个位置，每宠物 30 点 |
| 首次概览预热 | 每宠物第一次 overview 单列记录，非冷磁盘测试 | 同样单列记录 |
| 纯读取 | 并发 1、10、30，每档 6 秒 | 并发 1、4，每档 0.7 秒 |
| 读取接口 | latest、轨迹首屏 100 点、overview 轮询 | 相同接口 |
| 混合负载 | 分别启动 1 个和 3 个真实 Worker 子进程；20 台设备各顺序提交 10 个位置和 2 次原样重试，同时 10 个读客户端 | 每阶段 40 条唯一事件、8 次重试，同时 2 个读客户端 |
| 单个混合阶段的事件量 | 200 条唯一事件、40 次原样重试 | 40 条唯一事件、8 次原样重试 |

历史位置通过 SQL 夹具写入，用于查询真实表和索引，预置耗时不计为遥测处理吞吐。设备基线先确认在围栏内，再提交围栏外位置；对应告警和通知必须与设备数一致。所有对象为合成数据，不是实际项圈位置记录。

API 为独立进程；两个 Worker 阶段依次运行，每阶段结束后停止该阶段 Worker。读负载是 closed-loop：每个客户端收到响应后再发下一请求；写负载为突发，每台设备内部顺序发送，设备之间并发。该模型没有模拟持续固定到达率，也没有模拟 WAN 或第三方服务。

报告分接口记录 P50/P95/P99、错误数和读 RPS；混合阶段另列入队响应、排队、接收到投影完成、规则满足事件到投影完成、唯一事件处理速率及最新位置正确性。每 200ms 采样积压、advisory 等待和连接数，采样最大值可能漏过更短的瞬时峰值。另保留简化查询计划，不记录 SQL 参数或坐标。

## 如何判断结果

先检查正确性，再看延迟和吞吐。若存在重复投影、状态倒退、未处理队列、越权结果或进程/数据库未清理，即使请求很快也不算通过。

HTTP 每秒请求数与每秒唯一遥测事件数是不同指标；含重复消息的写请求不能全部计为新增事件处理吞吐。预置历史数据、启动预热和正式采样也要分开，不能把数据预置速度当成业务 API 性能。

P95 只描述报告中的样本。并发数越大不自动意味着承载用户数越多，短时突发处理成功也不能证明同样到达速率可以长期稳定运行。队列要同时核对处理延迟和最终积压，不能只记录 HTTP `202`。

## 事务与容量边界

当前 PostgreSQL 顶层写事务通过数据库级 advisory lock 延续 SQLite 的单写者顺序。多个 Worker 可以协作领取和完成任务，但写事务仍串行；增加 Worker 数量不等于已经实现写入吞吐的线性扩容。

保留该锁的理由是维持已有多步业务、幂等和队列语义。先以实测判断试点规模下是否满足目标，再决定是否按设备/宠物等资源细化锁；当前不预先替换整个事务模型。
