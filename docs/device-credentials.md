# 设备令牌与绑定码维护

本页说明现有设备独立令牌的轮换、吊销和预置设备绑定码补发。SQLite 与 PostgreSQL 使用同一业务合同；offline 仍通过本地模拟器、原遥测队列和 Worker 验证，无需真实供应商接口。

设备令牌用于设备身份，绑定码用于把预置设备认领给宠物，两者用途不同。补发绑定码不自动恢复被吊销的设备令牌，也不转移已有设备的所有权。

## 权限与状态

设备所有者与家庭共享角色是不同权限。共享成员能够照护宠物，不代表可以取得设备长期令牌。设备管理员由服务端 `DEVICE_ADMIN_USER_IDS` 用户 UUID 白名单单独配置，默认空名单；客服白名单 `SUPPORT_ADMIN_USER_IDS` 不授予设备管理员权限。

先以管理员账号登录，通过 `GET /api/v1/auth/me` 获取用户 UUID，再配置到所选环境文件并重启。不要使用未验证的邮箱文本直接授予管理员身份。原 `.env` 不会被工具覆盖；PostgreSQL 可继续使用独立 `.env.postgres`。

令牌在数据库中只保存散列及状态/版本元数据。轮换成功后旧令牌立即失效，新令牌只在本次响应提供；列表、设备详情与审计不提供明文令牌。含新令牌或绑定码的响应不进入通用幂等缓存。

## API 合同

接口统一前缀 `/api/v1`。维护接口使用已登录用户的 Bearer 令牌，不使用 `x-device-token`：

| 接口 | 权限与结果 |
| --- | --- |
| `GET /devices/{id}/credential` | 设备所有者读取当前凭证元数据；仍拥有但已解绑的设备也可读取 |
| `POST /devices/{id}/credential/rotate` | 设备所有者创建下一代令牌，响应一次性提供新 `device_token` |
| `POST /devices/{id}/credential/revoke` | 设备所有者吊销当前代令牌；不返回令牌 |
| `POST /admin/devices/{id}/credential/rotate` | 设备管理员仅为无所有者且无有效绑定的设备重发令牌，可恢复已释放且被吊销的设备 |
| `POST /admin/devices/{id}/claim-code` | 设备管理员仅为无所有者且无有效绑定的预置设备补发绑定码 |

POST 维护请求均提交原因，成功返回 HTTP `201`：

```json
{
  "reason": "设备维护后重新签发"
}
```

`reason` 去除前后空白后须为 1–500 字符。共享的 caregiver/viewer 不能因为能读取宠物资料就轮换令牌；设备管理员也不能替换已认领或仍有有效绑定的设备凭证。原来的设备所有者解绑后补发自己的绑定码，仍使用 `POST /devices/{id}/claim-code`。

凭证元数据为 `credential.version/status/changed_at`。`version` 表示密钥代数，首次预置为 1，每次轮换加 1；`status` 为 `active` 或 `revoked`。吊销改变当前代的状态，不增加密钥代数。重复吊销不会重复审计或刷新变更时间。

轮换响应包含 `device_id`、一次性 `device_token` 和新的 `credential` 元数据。设备详情、宠物概览的 `device` 和家庭运行简报的 `devices[]` 可向已有家庭成员显示 `credential` 状态与版本，但不会显示令牌散列或明文；专门的凭证读取/敏感维护接口仍只向设备所有者开放。

轮换和绑定码补发不缓存 `Idempotency-Key`。即使重复使用相同 Header，每次成功调用都会生成新的令牌或绑定码，使上一次结果失效。因此只在确实要再次签发时重试；不能依赖旧幂等键取回丢失的秘密。

新绑定码有效 30 分钟，补发会重置绑定码尝试次数，并让旧码失效；不会恢复设备令牌、修改既有所有权或认领已有设备。审计记录维护者、原因及相应版本或维护动作，签发响应中的令牌、绑定码及它们的散列不进入审计字段。维护原因也不要填写密钥。

SQLite `015-device-credentials.sql` 与 PostgreSQL `004-device-credentials.sql` 为已有设备增加凭证版本、状态和变更时间。原设备默认迁移为 `active/version=1`；变更时间回填设备创建时间，兼容旧导入缺少变更时间时的读取。

## 预置与离线联调

本地预置保留原命令，也可通过启动脚本执行，脚本先同步依赖与编译，再使用选定环境文件预置设备，完成后退出：

```powershell
# SQLite，按 .env 选择本地数据库。
./start.bat .env provision SIM-CREDENTIAL-SQLITE-001

# PostgreSQL，按独立配置选择数据库。
./start.bat .env.postgres provision SIM-CREDENTIAL-PG-001
```

预置是有数据库访问权的本地维护操作，不是面向未登录用户的公开 API。命令会一次性输出设备令牌、绑定码和 `active/version=1` 元数据，供模拟器/设备维护人员安全交接，不能把整段终端输出发送到应用日志。可选 vendor/model 参数仍通过 `npm.cmd run provision -- <serial> [vendor] [model]` 提供；BAT 维护入口只接收序列号。

调用轮换后，将新令牌配置给模拟器的 `DEVICE_TOKEN`，再使用原 `import:offline` 或 `simulate:device` 命令。模拟器令牌更新不替代真实固件的安全密钥下发。

## 吊销与已接收数据

吊销阻止后续设备访问。直连遥测、命令轮询、命令回执和供应商 HMAC 入口都必须检查设备凭证状态；供应商签名通过不能绕过设备吊销。

遥测在入队事务内部认证当前散列和状态，再检查事件幂等或写入，因此等待事务锁期间发生的轮换/吊销也会生效。命令轮询和回执在到期维护后重新认证，不依赖维护前读取的旧凭证状态。

供应商标准入口仍以 HMAC 认证发送方，不需要知道每台设备的新长期令牌。仅轮换设备令牌不会轮换供应商 HMAC 密钥；吊销设备后，供应商即使持有有效 HMAC 密钥也不能继续为它接收新消息。

已经持久化接收的消息继续由原 Worker 按已有绑定快照、时间与质量规则处理。吊销不追溯删除已接收队列，不撤回已经发出的命令，也不声称真实固件已停止或手机已收到通知。

## 本地运行与交接边界

offline 模式可验证令牌失效、轮换后的上报和本地命令回执，但它不完成真实设备的新密钥安全下发、证书烧录、供应商侧凭证失效或 KMS 管理。更新模拟器的 `DEVICE_TOKEN` 后使用原上报/模拟命令继续联调，不能把新令牌写入源码或普通应用日志。

旧令牌立即失效，没有自动双令牌重叠窗口。执行轮换前确认有可用的设备更新渠道；响应丢失后不能从读取接口取回同一明文令牌，需要有权限的操作者重新轮换。

## 备份恢复后的凭证核对

数据库归档保存的是备份时的令牌散列、状态和版本。快照完成后的轮换或吊销不会自动回放到恢复副本；较早、没有凭证元数据的归档正常升级后，旧设备会采用 `active/version=1` 默认值。这不表示后来的吊销结果仍然有效。

恢复演练继续使用独立数据库、loopback 监听和 offline 模式。正式切换前核对备份之后的设备维护记录，并按需要重新轮换或吊销；不要把旧快照中的凭证状态直接当成当前生产授权。数据库恢复步骤见 [database-operations.md](database-operations.md)。
